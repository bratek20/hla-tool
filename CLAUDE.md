# hla-tool

HLA code generator: turns `.module` files into Kotlin, TypeScript and C# code (API types, web layer, fixtures).
Open source (GitHub `bratek20/hla-tool`, branch `main`, PRs on GitHub). WoH repos consume it as `tool.jar` in their
`hla` submodule.

Gradle modules: `code-builder/` (language-agnostic code DSL), `lib/` (parsing + generation), `app/` (CLI),
`example/` (golden files + `example/tests/` that compile and run them).

## Self-hosting

- HLA generates its own code. Its definitions live in `hla/*.module` (not `example/hla/`).
- Generated files under `lib/` (header `DO NOT EDIT! Autogenerated by HLA tool`) must not be hand-edited:
  change `hla/*.module`, then `cd bash && ./updateModule.sh <Module>` (`./allModulesUpdate.sh` for all).
- Self-hosting regenerates with the latest **released** tool, not the local build: `bash/tool.jar`, downloaded by
  `cd bash && ./hlaToolUpdate.sh` (version in `bash/toolVersion.txt`). Generator changes reach HLA's own code only
  after a release.

## Orientation map

Facts that are expensive to rediscover. If one turns out wrong, fix it here.

### The funnel

- `PatternGenerator` (`lib/.../generation/impl/core/Generators.kt`) is the spine. Velocity
  (`!supportsCodeBuilder()`, the default) and code builder (`getOperations()`/`getOperationsPerFile()`) both end in
  `generatePatternFile()`, which adds the DO NOT EDIT header. `getFiles()`/`getDirectory()` (InitSql, Examples JSON)
  bypass it.
- Cross-cutting transforms of generated text belong in `generatePatternFile()` (the modern TS transform hooks there).
- Extension points: `patternName()`, `mode()` (`ONLY_START`: no header, skipped on update), `supportsCodeBuilder()`,
  `shouldGenerate()`, `doNotGenerateTypeScriptNamespace()`, `useImportsCalculator()`, `shouldSkip()` (profile
  `onlyPatterns`/`skipPatterns`).

### Three "language" abstractions

| Abstraction | Location | Level |
|---|---|---|
| `LanguageSupport` | `lib/.../generation/impl/core/language/` + `impl/languages/<lang>/<Lang>Support.kt` | per-language services: types, extension, fixtures, `base()` |
| `CodeBuilderLanguage` | `code-builder/.../core/Languages.kt` | syntax: keywords, list/map/optional forms |
| `LanguageTypes` | `lib/.../generation/impl/core/language/LanguageTypes.kt` + `<Lang>Types.kt` | string templates for velocity/legacy |

- `ModuleGeneratorLogic` is the only place `ModuleLanguage` maps to `LanguageSupport`; `<Lang>Support.base()` is the
  only production place a `CodeBuilderLanguage` is created.
- `CodeBuilderContext` carries only `lang`, no profile: profile-driven behaviour goes through a language constructor
  arg (`TypeScript(modern)`) or stays in `lib/`.

### TypeScript: code builder vs velocity

- Code builder: `Enums`, `EnumValues`, `Exceptions`, `Events`, `Mocks`, `TestBase`, `PlayFabHandlers`,
  `WebServerContext`, `Menu`, `Track`, `InitSql`, Examples.
- Velocity (`lib/src/main/resources/templates/type_script/`): everything else (`ValueObjects`, `DataClasses`,
  `Interfaces`, `Builders`, `Diffs`, `Asserts`, `Logic`, `ImplContext`, `Web*`, keys, `CustomTypes*`, `ImplTest`).
  `ValueObjects` is code builder only for C#.
- Some `.vm` files declare their own `namespace`; the rest are wrapped in `Generators.kt`. `ImplGenerator.kt` injects
  `namespace <M>.Impl {` by string surgery. Templates get `moduleName` and `modern` via `contentBuilder()`.

### Files and directories

- File name = `PatternName` + extension. Only exception: `Events` → `Notifications.ts` (`EventsGenerator`).
- Directory layout rules live in `lib/.../writing/impl/ModuleWriterLogic.kt` (`calcModuleDirectoryName`,
  `calcSubmoduleDirectoryName`, `HlaSrcPaths.getPathForSubmodule`). Reuse them. Relative ESM specifiers:
  `writing/impl/RelativePaths.kt`.

### TypesWorld limits

`TypesWorldApi` (`lib/.../typesworld/`) is the type registry; `HlaTypePath` = `[groups/]<Module>/<Submodule>/<Pattern>`;
`ImportsCalculator` derives Kotlin/C# imports from it. Populators: `lib/.../hlatypesworld/impl/`, registered in
`hlatypesworld/context/Impl.kt`.

- Only submodules `Api`, `ViewModel`, `View`, `Impl` (Track only) are populated.
- Only Api patterns `ValueObjects`, `DataClasses`, `CustomTypes`, `Events`, `Enums` (name only) are populated.
  `Interfaces`, `Exceptions`, keys, `CustomTypesMapper`, `SerializedCustomTypes` are absent.
- Dependencies come only from structure (`extends`, field types, type args, one hop). Method signatures, bodies and
  const initializers are invisible.
- `ensureType` enforces global name uniqueness (`SameNameTypeExistsException`): don't register speculative names.
- `mapToImport` drops the last path segment, so it can't produce a file-level specifier.

### Parsing

- `lib/.../parsing/impl/ModuleGroupParserLogic.kt`. A new root section must be added to `knownRootSections`
  (else `UnknownRootSectionException`). Follow `parseKotlinConfig`/`parseTypeScriptConfig`.
- Syntax reference: `example/hla/*.module`.
- `EnumValues` entries are the closed set of allowed content values for the populated type (`EnumValuesValidator` in
  `validations/impl/Logic.kt`), so a type used as `idSource` must not be populated there. C# skips the pattern.

### Profiles (`properties.yaml`)

- Unknown keys are silently dropped. A key that "does nothing" usually means the field is missing in `hla/Facade.module`.
- `FilesModifiers` (`writing/impl/`) maintains tsconfig, package.json, launch.json and entry, each only if the profile
  declares its path. Skipped when `onlyUpdate` (so `update`/`updateAll` never touch them).
- It registers every submodule that produced a `.ts` file (`Fixtures`/`Tests` → test tsconfig). Don't reintroduce a
  hardcoded submodule list.

## Code builder rules

- Never use `hardcodedExpression()` when a typed builder exists; add a builder instead (pattern:
  `code-builder/.../builders/SimpleExpressionBuilders.kt`).
- Language-specific syntax belongs in the language backend (`Languages.kt`), not in pattern generators.
- Check `code-builder/.../builders/` for an existing builder before writing one.

## Testing

- `HlaFacadeTest` is a golden-file test: it generates into `example/<lang>/` and compares. It also runs
  `FilesModifiers`, so it mutates committed tsconfig/package.json/launch.json/entry files.
- When `example/hla/SomeModule.module` or generator output changes, regenerate examples for ALL profiles
  (`kotlin`, `typeScript`, `cSharp`, `kotlinSkipPatterns`), or other profiles' tests fail:
  `cd example && java -jar ../app/build/libs/app.jar update hla <profile> <Module>` (`updateAll` for every module of a
  profile; run configs in `.run/`).
- Parser changes: `ModuleGroupParserTest` + `lib/src/test/resources/parsing/<case>/`.
- For file-text edits, extract pure `List<String> -> List<String>` helpers (`writing/impl/ModernFileEdits.kt`,
  `TsConfigEdits.kt`, tested in `writing/tests/`).

## Modern TypeScript (ESM)

Legacy TS is global-scope (`namespace` blocks, ordered tsconfig `files`). Modern is real ES modules; reference
implementation: aircombatcs `Modern/Src/DeepLinks` and `Modern/Test/DeepLinks`.

- Opt-in needs both: profile `typeScript.modern: true` (plus `entryPath`, `vitestConfigPath`) and a `TypeScript`
  section with `modern = true` in the `.module`. `isModernModule()` in `generation/impl/languages/typescript/Modern.kt`.
  One profile normally mixes migrated and legacy modules.
- Code: `ModernTypeScriptSource.kt` (namespace unwrap, exports), `ModernTypeScriptPaths.kt` (path → specifier),
  `ModernTypeScriptExports.kt` (registry for what TypesWorld lacks), `ModernTypeScriptTransformer.kt` (orchestration).

Load-bearing rules:
- Import only from modern modules of the same group; legacy modules keep `Module.X.y` globals.
- `ImplContext` must be `export const Api = { … }` (Mocks assign to `Api.someMethod`).
- `Diffs.ts` hoists the narrowed optional into a local before `forEach` (`ExpectedTypeField.localName()`).
- `TestBase` must not export `test` (vitest provides it).
- Ambient legacy globals (`Optional`, `STRING`, `Class()`, `HandlerContext`, `StringEnumClass`, `Undefined`,
  `AssertEquals`, `DependencyName`, `Ts.E2E`) are never imported. `= STRING`/`= Class(X)` initializers must survive
  (`useDefineForClassFields: false` in the consumer).
- Builder/assert names and the `c` context variable are registered qualified-only; bare names collide with fields.
- A `Module.Builder.X` reference into the file being generated must collapse to bare `X`.
- `ModernTypeScriptExports` registers what a pattern actually emits. Exceptions come from
  `ModuleGroupQueries.allExceptionNamesForCurrent()` (includes `throws` clauses); doc-comment `@throws` never drive
  imports (`isCommentLine`).

## Style

- Comments only for non-obvious "why".
- Explicit imports, no fully qualified names in code.

## Release

- Pushing an `x.y.z` tag triggers `.github/workflows/release.yml`: builds `app:build` and publishes `hla-tool.jar`
  as a GitHub release. Consuming repos update with `cd hla && ./hlaToolUpdate.sh` (writes `tool.jar` and
  `toolVersion.txt`).
